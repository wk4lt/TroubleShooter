# 日志故障定位规范

## 目标

当用户描述某个线上故障(服务报错、接口异常、超时、500 等)时,按照本规范从日志出发,
层层收窄范围,最终定位到根因,并给出可执行的修复建议。

## 排查步骤

1. **确认故障现象与时间窗**
   - 问清(或从用户描述中提取):影响的服务/接口、大致发生时间、错误码或异常表现。
   - 时间窗是日志检索的第一道过滤器。

2. **先看错误与堆栈**
   - 优先找 `ERROR` / `CRITICAL` / `Traceback` / `Exception` 关键字。
   - 堆栈的最后一帧通常是根因所在,但也要向上翻看调用链,确认是「源头」而非「被波及」。

3. **按请求链路追踪**
   - 用 trace id / request id / session id 关联同一请求的多条日志。
   - 区分:是上游调用超时、下游依赖失败、还是自身逻辑抛错。

4. **对比正常与异常**
   - 找同接口的近期正常请求日志做对比,看差异(参数、耗时、返回大小、依赖调用)。

5. **逐层定位**
   - 网络层 → 网关 → 应用逻辑 → 数据库/缓存/外部服务,逐层排除。
   - 常见根因类型:空指针/索引越界、超时、连接池耗尽、磁盘/内存打满、配置错误、依赖不可用。

## 常见日志关键字

- `TimeoutError` / `timed out` —— 依赖或网络超时
- `Connection refused` / `Connection reset` —— 目标服务不可达或被杀
- `OutOfMemory` / `MemoryError` / `OOM` —— 内存不足
- `DiskFull` / `No space left on device` —— 磁盘打满
- `Deadlock` / `Lock wait timeout` —— 锁等待/死锁
- `NullPointerException` / `NoneType` / `AttributeError` —— 空值/属性错误
- `IndexError` / `ArrayIndexOutOfBounds` —— 越界
- `too many connections` / `connection pool exhausted` —— 连接池耗尽

## 结论输出格式

按以下结构输出,方便直接排障:

```
## 故障定位报告

- 现象:...
- 时间窗:...
- 根因:<一句话根因>
- 证据:<关键日志片段 / 堆栈关键帧>
- 影响范围:...
- 建议修复:<按优先级列出 1..n>
- 临时止血方案:<如有>
```

## 注意事项

- 只基于真实日志与工具返回的数据下结论,没有证据的部分明确标注「未确认」。
- 不要臆造日志内容;若工作区没有日志文件,先用 list_files 查看有哪些文件可用。
- 结论要区分「已定位根因」与「仍需更多日志」,必要时告诉用户需要补充哪些日志。
